# Требования к сервисам

[Оглавление](README.md)

## Проверка ответа

Сервис 2 пропускает финальный результат только если:

- JSON-RPC `id` совпадает с запросом;
- присутствует ровно одно из полей `result` или `error`;
- у `result` поле `resultType` равно `complete`;
- `inputRequests` и `requestState` отсутствуют;
- каждый элемент `content` имеет `type: "text"` и строковое поле `text`;
- `isError` — логическое значение или отсутствует;
- `structuredContent`, если он есть, соответствует `return_parameters` из конфигуратора.

## Таймауты

Нужно различать idle timeout и абсолютный timeout прокси.

```text
H < min(T_idle_2, T_idle_sowa)
```

Рекомендуется `H <= min(...) / 2`. Heartbeat — SSE-комментарий `: keep-alive`. Он проходит сервис 2 и SOWA без буферизации, но не отменяет абсолютный timeout.

Общий дедлайн:

```text
таймаут сервиса 1
  > таймаут сервиса 2
    > таймаут SOWA
      > максимальное время инструмента сервиса 4
```

Плановая ротация и повтор через GET отсутствуют. Абсолютный timeout завершает вызов как `MCP_RESULT_UNKNOWN`.

## Требования к сервису 1

Сервис 1 должен:

1. Отправлять версию `2026-07-28` заголовком и в `_meta` каждого POST.
2. Передавать `clientInfo` и пустые `clientCapabilities`.
3. Ставить `Mcp-Method`, а для инструмента ещё и `Mcp-Name`.
4. Не отправлять `initialize` и не ожидать `MCP-Session-Id`.
5. Принимать JSON или конечный SSE на том же POST.
6. Принимать progress только с ожидаемым `progressToken`.
7. Проверять `resultType: "complete"` и тип `text`.
8. Не открывать `GET /mcp`.
9. Не повторять `tools/call` после обрыва или `input_required`.
10. Возвращать `MCP_RESULT_UNKNOWN`, если финальный ответ не получен.

## Требования к сервису 2

Сервис 2 должен:

1. Разрешать только `POST`.
2. Проверять путь разрешённого MCP-сервера.
3. Сверять `Mcp-Method`, `Mcp-Name`, JSON-RPC `method` и `params.name`.
4. Сверять версию заголовка и `_meta`.
5. Проверять allowlist тулы, права и rate limit по паре «ДЗО + toolName».
6. Запрещать batch, `task` и посторонние поля `_meta`.
7. Передавать запрос в SOWA без изменения JSON-RPC-полей и протокольных заголовков.
8. Потоково проверять SSE.
9. Блокировать любой `content.type`, кроме `text`, и любой `input_required`.
10. Ограничивать размер, длительность и число SSE-событий.

Состояние MCP-сессии между pod не требуется: каждый POST независим. Для rate limit нужен общий счётчик, если у сервиса 2 несколько pod.

Повторный GET не используется, поэтому квота `tools/call` списывается на каждый POST один раз.

## Требования к SOWA

Корень тела — один JSON-объект. Массив запрещён.

Для `Mcp-Method: server/discover` SOWA проверяет:

- `method` строго `server/discover`;
- `id` присутствует;
- версия в `_meta` строго `2026-07-28`;
- `clientCapabilities` — пустой объект;
- `arguments` и `name` отсутствуют.

Для `Mcp-Method: tools/call` SOWA выбирает заранее скомпилированную схему по `Mcp-Name`:

- `method` строго `tools/call`;
- `params.name` совпадает с заголовком;
- `arguments` соответствуют схеме инструмента;
- обязательные ключи `_meta` присутствуют;
- `task`, `inputResponses` и `requestState` отсутствуют.

Схемы всех инструментов не объединяются в один большой `oneOf`.

SOWA не изменяет тело и протокольные заголовки, передаёт SSE без буферизации и не применяет request-схему к ответу.

## Требования к сервису 4

Сервис 4 должен:

1. Реализовать `server/discover` и `tools/call` версии `2026-07-28`.
2. Не требовать `initialize` и `MCP-Session-Id`.
3. Возвращать `400`, если версия заголовка не совпадает с `_meta`.
4. Возвращать `-32022`, если версия сервером не поддерживается.
5. Объявлять только capability `tools`.
6. Повторно проверять имя инструмента, аргументы, права и собственный rate limit.
7. Возвращать JSON или конечный SSE на том же POST.
8. Завершать успешный вызов через `resultType: "complete"` и только текстовый `content`.
9. Не возвращать `input_required`.
10. Не отправлять встречные JSON-RPC-запросы.
11. Отправлять progress только при наличии `progressToken`.
12. Завершать SSE до абсолютного таймаута прокси.

Любой экземпляр сервиса 4 может обработать любой POST. Общее состояние нужно только для rate limit и бизнес-данных самого инструмента, а не для MCP-сессии.

## Ошибки

- HTTP 405 — метод кроме POST.
- HTTP 400 — расхождение заголовков и тела либо неверная структура.
- HTTP 403 — тула, метод или права не разрешены.
- HTTP 413 — превышен размер.
- HTTP 415 — неверный `Content-Type`.
- HTTP 429 — превышен rate limit тулы.
- JSON-RPC `-32600` — неверный envelope.
- JSON-RPC `-32602` — неверные аргументы.
- JSON-RPC `-32022` — неподдерживаемая версия протокола.
- HTTP 504 / `MCP_RESULT_UNKNOWN` — обрыв или таймаут до финального ответа.

## Приёмочные проверки

1. `tools/call` выполняется без предшествующего `initialize`.
2. `server/discover` не создаёт состояние, обязательное для следующего вызова.
3. Расхождение `MCP-Protocol-Version` и `_meta` даёт HTTP 400.
4. `Mcp-Name`, не совпадающий с `params.name`, отклоняется.
5. JSON-ответ содержит `resultType: "complete"` и тот же `id`.
6. SSE завершается финальным ответом на том же POST.
7. `content.type`, отличный от `text`, блокируется сервисом 2.
8. `input_required` блокируется и не приводит к повторному POST.
9. `GET /mcp` и `DELETE /mcp` отклоняются.
10. Обрыв SSE даёт `MCP_RESULT_UNKNOWN` без автоматического повтора.
11. Запрос с пустым `clientCapabilities` не получает встречный JSON-RPC.
12. Rate limit действует отдельно для каждой тулы.
