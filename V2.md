# Вариант V2 — MCP 2025-11-25 с разрешённым GET /mcp

## Отличие от V1

Архитектура остаётся прежней:

```text
Сервис 1 → Сервис 2 → SOWA → Сервис 4
```

В V2:

- разрешён `GET /mcp`;
- разрешён заголовок `Last-Event-ID`;
- разрешено возобновление оборванного SSE;
- учитываются idle timeout и абсолютный timeout прокси;
- сервис 4 хранит историю SSE-событий, необходимую для replay;
- клиент не повторяет `tools/call`, а продолжает его через GET;
- JSON Schema-валидация POST-запросов остаётся такой же, как в V1.

Функциональный allowlist MCP не расширяется. Разрешены только:

- `initialize`;
- `notifications/initialized`;
- `tools/call`;
- `notifications/progress`;
- финальный JSON-RPC `result` или `error`.

`GET /mcp` добавляется как транспортный механизм. Он не разрешает автоматически
`sampling`, `elicitation`, `roots`, `resources`, `prompts`, `logging`, `tasks` или
другие MCP-возможности.

## Назначение GET /mcp

В V2 GET применяется в первую очередь для возобновления SSE, который был открыт ответом
на `POST tools/call`.

Пример:

```text
POST /mcp tools/call
  → HTTP 200 text/event-stream
  → event id=evt-1: progress
  → event id=evt-2: progress
  → соединение оборвалось по таймауту

GET /mcp
MCP-Session-Id: session-123
Last-Event-ID: evt-2
  → event id=evt-3: progress
  → event id=evt-4: final result
```

Отдельный постоянный GET без `Last-Event-ID` технически разрешён, но в текущем
ограниченном профиле не несёт прикладных MCP-сообщений. Для включения асинхронных
уведомлений или server-to-client requests потребуется отдельное расширение policy.

## Разрешённые HTTP-методы

### POST /mcp

Разрешён для:

- `initialize`;
- `notifications/initialized`;
- `tools/call`.

Ответом может быть:

- `application/json`;
- `text/event-stream`.

### GET /mcp

Разрешён для:

1. возобновления оборванного SSE с `Last-Event-ID`;
2. опционального открытия отдельного SSE-канала без прикладных сообщений текущего
   профиля.

GET не содержит тела и не проходит JSON Schema-валидацию.

### DELETE /mcp

Опционально разрешён для завершения MCP-сессии.

### Остальные HTTP-методы

`PUT`, `PATCH`, `OPTIONS` в роли MCP-вызова и другие методы запрещены.

## Инициализация

Инициализация совпадает с V1.

Запрос:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-11-25",
    "capabilities": {},
    "clientInfo": {
      "name": "service-1",
      "version": "1.0.0"
    }
  }
}
```

Допустимый ответ:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2025-11-25",
    "capabilities": {
      "tools": {
        "listChanged": false
      }
    },
    "serverInfo": {
      "name": "service-4",
      "version": "1.0.0"
    }
  }
}
```

Сервер может вернуть:

```http
MCP-Session-Id: session-123
```

После этого клиент отправляет:

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/initialized"
}
```

Поддержка GET и resumability не объявляется capability в `initialize`. Она определяется
интеграционным контрактом и проверяется тестами.

## Обычный tools/call

```json
{
  "jsonrpc": "2.0",
  "id": 18,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": {
      "city": "Warsaw"
    },
    "_meta": {
      "progressToken": "progress-18"
    }
  }
}
```

Ограничения:

- tool входит в allowlist;
- arguments соответствуют схеме инструмента;
- `params.task` отсутствует;
- в `_meta` разрешён только `progressToken`;
- клиент принимает JSON или SSE на том же POST.

## Требования к SSE

Каждое SSE-событие должно иметь `id`:

```text
id: evt-session-123-stream-18-0001
data: {"jsonrpc":"2.0","method":"notifications/progress","params":{"progressToken":"progress-18","progress":40,"total":100}}

```

Финальное событие:

```text
id: evt-session-123-stream-18-0004
data: {"jsonrpc":"2.0","id":18,"result":{"content":[{"type":"text","text":"Готово"}],"isError":false}}

```

Требования:

1. Event ID уникален как минимум в рамках MCP-сессии.
2. Event ID однозначно связан с исходным SSE-потоком.
3. Сервис 4 сохраняет событие до истечения окна replay.
4. Progress использует token исходного `tools/call`.
5. Progress не уменьшается.
6. Финальный ответ содержит id исходного JSON-RPC-запроса.
7. После финального ответа события этого потока запрещены.

## Возобновление через GET

После обрыва клиент отправляет:

```http
GET /mcp HTTP/1.1
Accept: text/event-stream
MCP-Protocol-Version: 2025-11-25
MCP-Session-Id: session-123
Last-Event-ID: evt-session-123-stream-18-0002
```

Тело отсутствует.

Сервис 4 должен:

1. проверить MCP-сессию;
2. проверить принадлежность event ID этой сессии;
3. определить исходный поток;
4. повторить события после указанного ID;
5. продолжить поток до финального `result` или `error`.

Если event ID неизвестен или история уже удалена, сервер не должен выдавать результат
другого потока. Интеграция возвращает `MCP_RESULT_UNKNOWN`.

## Таймауты

Необходимо различать:

- **idle timeout** — соединение закрывается, если некоторое время нет байтов;
- **absolute timeout** — соединение закрывается после фиксированной длительности,
  независимо от активности.

Обозначения:

```text
T_idle_2    — idle timeout сервиса 2
T_idle_sowa — idle timeout SOWA
T_max_2     — абсолютный timeout сервиса 2
T_max_sowa  — абсолютный timeout SOWA
T_call      — общий дедлайн tools/call на сервисе 1
H           — интервал SSE heartbeat
R           — момент плановой ротации SSE
```

Требования:

```text
H < min(T_idle_2, T_idle_sowa)
```

Рекомендуется:

```text
H <= min(T_idle_2, T_idle_sowa) / 2
```

Для абсолютного timeout:

```text
R < min(T_max_2, T_max_sowa)
```

Ротация выполняется с запасом до закрытия прокси.

Общий дедлайн:

```text
T_call > суммарное время POST + всех GET-reconnect
```

Но `T_call` остаётся конечным. Reconnect не должен продолжаться бесконечно.

## Heartbeat

Чтобы избежать idle timeout, сервис 4 периодически отправляет SSE comment:

```text
: keep-alive

```

Комментарий:

- не является JSON-RPC-сообщением;
- игнорируется сервисом 1;
- передаётся сервисом 2 и SOWA без буферизации;
- обновляет сетевую активность;
- не предотвращает absolute timeout.

## Плановое закрытие потока

Если приближается абсолютный timeout, сервер может завершить HTTP-соединение, не завершая
логический SSE-поток.

Перед закрытием рекомендуется отправить:

```text
retry: 1000
id: evt-session-123-stream-18-0042
data:

```

Клиент:

1. сохраняет последний event ID;
2. ждёт значение `retry`;
3. выполняет GET с `Last-Event-ID`;
4. продолжает ждать исходный JSON-RPC `id=18`.

## Требования к сервису 1

Сервис 1 должен:

1. Выполнить обычный lifecycle MCP.
2. Сохранять session id.
3. Поддерживать потоковое чтение SSE из POST и GET.
4. Сохранять последний SSE event ID для каждого активного потока.
5. После обрыва выполнять GET с session id и `Last-Event-ID`.
6. Учитывать серверный `retry`.
7. Ограничивать число reconnect и общий дедлайн вызова.
8. Продолжать корреляцию с исходным JSON-RPC `id`.
9. Не отправлять повторный `tools/call`.
10. Возвращать `MCP_RESULT_UNKNOWN`, если resume невозможен.
11. Не принимать методы вне утверждённого allowlist.

## Требования к сервису 2

### POST

Требования V1 сохраняются:

- method allowlist;
- tool allowlist;
- проверка прав;
- проверка protocol/session headers;
- проверка JSON/SSE response;
- корреляция progress и финального ответа.

### GET

Сервис 2 должен проверять:

- путь строго `/mcp`;
- тело отсутствует;
- `Accept` содержит `text/event-stream`;
- protocol version равна `2025-11-25`;
- session id присутствует;
- `Last-Event-ID` присутствует для resume;
- длина и допустимые символы event ID;
- отсутствие запрещённых query parameters.

Сервис 2 передаёт `Last-Event-ID` без изменения.

### Состояние между pod

После reconnect GET может попасть на другой pod сервиса 2. Для полной семантической
валидации resumed stream требуется один из вариантов:

1. общее хранилище контекста активных потоков;
2. маршрутизация session/stream на тот же pod;
3. проверяемый event ID, содержащий подписанный stream context.

Без одного из этих механизмов сервис 2 может проверить только синтаксис GET и отдельных
SSE-событий, но не сможет доказать, что финальный JSON-RPC id относится к исходному POST.

Рекомендуемый вариант: сервис 4 является владельцем replay-state и проверяет event ID,
а сервис 2 использует общее минимальное состояние корреляции либо sticky routing.

## Требования к SOWA

### POST

JSON Schema остаётся как в V1:

```text
oneOf:
  - InitializeRequest
  - InitializedNotification
  - CallToolRequest
```

Для tools/call используется отдельная схема arguments для каждого `params.name`.

### GET

GET не содержит JSON body. SOWA не применяет к нему JSON Schema.

SOWA должна проверять HTTP-policy:

- метод GET разрешён только на `/mcp`;
- `Accept: text/event-stream`;
- protocol version;
- session id;
- опциональный или обязательный `Last-Event-ID` в зависимости от режима;
- отсутствие тела;
- ограничения длины заголовков;
- отсутствие запрещённых query parameters.

SOWA должна:

- передавать `Last-Event-ID` без изменения;
- отключить response buffering;
- передавать heartbeat и SSE-события сразу;
- не пытаться интерпретировать SSE response как JSON request;
- иметь timeout, согласованный с heartbeat и ротацией.

## Требования к сервису 4

Сервис 4 должен:

1. Поддерживать `POST /mcp`, `GET /mcp` и опционально `DELETE /mcp`.
2. Выдавать event ID всем SSE-событиям, которые могут потребовать replay.
3. Хранить event history в течение согласованного replay TTL.
4. Проверять связь session id, event ID и stream.
5. Поддерживать GET с `Last-Event-ID`.
6. Повторять только события исходного потока после указанного ID.
7. Периодически отправлять heartbeat чаще минимального idle timeout.
8. Планово ротировать соединение раньше абсолютного timeout.
9. Завершать логический поток финальным JSON-RPC `result` или `error`.
10. Не инициировать запрещённые MCP-методы.
11. Возвращать HTTP 404 для неизвестной/просроченной сессии.
12. Не переиспользовать event ID между активными потоками одной сессии.

Если сервис 4 развёрнут в N экземплярах, replay-state должен быть:

- доступен всем экземплярам; или
- запрос должен маршрутизироваться на владельца session/stream.

Обычная случайная балансировка без общего state не обеспечивает resumability.

## Разрешённые сообщения в GET SSE

В текущем профиле разрешены только:

- replay ранее отправленного `notifications/progress`;
- новые `notifications/progress` исходного активного вызова;
- финальный `result` или `error` исходного вызова;
- SSE comments и поля `retry`.

Запрещены:

- `sampling/createMessage`;
- `elicitation/create`;
- `roots/list`;
- list-changed notifications;
- resources notifications;
- logging notifications;
- task notifications;
- любые неизвестные server-to-client methods.

## Ошибки GET/reconnect

- `405 Method Not Allowed` — GET не поддерживается фактическим endpoint; resume невозможен.
- `400 Bad Request` — неверные заголовки или event ID.
- `403 Forbidden` — запрос не разрешён policy.
- `404 Not Found` — сессия или stream больше не существуют.
- `409 Conflict` — event ID не соответствует сессии/потоку, если сервер использует такой код.
- `410 Gone` — replay history уже удалена, если сервер использует такой код.
- `504 Gateway Timeout` — очередное соединение закрыто прокси.

Во всех случаях, когда продолжить исходный поток невозможно, результат вызова —
`MCP_RESULT_UNKNOWN`. Повторный `tools/call` автоматически не отправляется.

## Приёмочные проверки V2

1. Инициализация и обычный JSON tools/call работают как в V1.
2. SSE tools/call получает event IDs.
3. Heartbeat проходит через сервис 2 и SOWA без буферизации.
4. Idle timeout не наступает при корректном heartbeat.
5. Absolute timeout приводит к закрытию соединения и последующему GET reconnect.
6. GET без тела проходит HTTP-policy SOWA.
7. GET с неверным session id отклоняется.
8. GET с неизвестным `Last-Event-ID` не возвращает события другого потока.
9. После reconnect повторяются только пропущенные события.
10. Финальный JSON-RPC id после reconnect совпадает с исходным tools/call.
11. Запрещённый server-to-client method внутри GET SSE блокируется.
12. После истечения replay TTL возвращается контролируемая ошибка.
13. Количество reconnect и общий дедлайн ограничены.
14. При невозможности resume клиент возвращает `MCP_RESULT_UNKNOWN`.
