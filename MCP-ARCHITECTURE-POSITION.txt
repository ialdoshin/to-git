Позиция по использованию MCP

Целевая архитектура предполагает подключение более 20 ДЗО и потенциально большого
количества инструментов:

Brain (MCP Client)
        ↓
Cross-hub (Policy Proxy)
        ↓
SOWA (JSON Schema validation)
        ↓
Cross-hub-ext (MCP/SberACL Proxy)
        ↓
MCP-DZO (MCP Server конкретного ДЗО)

Brain уже поддерживает MCP 2025-11-25 и транспорт Streamable HTTP, а при необходимости
может вызывать обычные REST API. Поэтому для работы по MCP не требуется разрабатывать
в Brain новый транспортный или клиентский слой.

Предлагается использовать MCP по всему тракту. При этом речь идёт не о разрешении всех
возможностей MCP, а о контролируемом профиле с фиксированной версией, ограниченным
набором методов, централизованной валидацией, авторизацией, rate limit и
наблюдаемостью.

Предлагаемое решение

Для новых интеграций предлагается использовать MCP по всему тракту: Brain (MCP Client)
→ IAG → Cross-hub → SOWA → Cross-hub-ext → MCP-DZO (MCP Server).

На первом этапе разрешить только:

- initialize;
- notifications/initialized;
- tools/call;
- notifications/progress;
- финальный result или error.

Запретить:

- sampling;
- elicitation;
- resources;
- prompts;
- roots;
- logging;
- tasks;
- неизвестные методы;
- server-to-client requests.

Таким образом, MCP используется как унифицированный протокол вызова инструментов, а не
как неконтролируемый двунаправленный канал.

1. Требование единообразия не означает, что обязательно нужен REST

Цель единообразия правильная. Но REST сам по себе не создаёт единый контракт.

При большом количестве ДЗО REST обычно приводит к появлению:

- разных endpoint;
- разных DTO;
- разных форматов ошибок;
- разных правил версионирования;
- отдельных клиентских методов;
- индивидуальных OpenAPI-спецификаций.

MCP уже стандартизует:

- lifecycle подключения;
- формат вызова инструмента;
- имя и аргументы инструмента;
- JSON Schema входных параметров и схему результата;
- единый формат успешных результатов и ошибок;
- версионирование протокола.

Поэтому MCP даёт единообразие на уровне семантики вызова, тогда как REST без
дополнительного стандарта даёт только общий транспорт HTTP.

2. Нагрузка на сопровождение

Нагрузка на сопровождение определяется не названием протокола, а количеством
контрактов, преобразований, уникальных реализаций и компонентов, которыми необходимо
управлять.

В предлагаемой архитектуре сервис Brain уже является MCP-клиентом, а сервисы MCP-DZO
реализуют единый MCP Server. Сервис Cross-hub и SOWA являются общими платформенными
компонентами для всех ДЗО. Поэтому расширение контура выполняется по одному
утверждённому шаблону, без создания отдельного интеграционного протокола для каждого
подключения.

Для общего тракта можно использовать единый формат адреса:
/mcp/{dzo}/{server}. По этому пути Cross-hub однозначно определяет целевое ДЗО и
конкретный MCP Server. При добавлении новой тулы в существующий MCP Server не требуется
создавать отдельный сетевой маршрут: таблица маршрутизации растёт по количеству
MCP-серверов, а не по количеству tools. Это упрощает настройку, эксплуатацию и
диагностику, а также снижает вероятность ошибки при ручном заведении маршрутов.
Настройки прав, схем и лимитов для отдельных tools при этом остаются в конфигураторе и
не смешиваются с сетевой маршрутизацией.

Обязательный REST→MCP adapter, наоборот, добавляет отдельный компонент и второй
интеграционный контракт:

- нужно поддерживать REST-контракт;
- MCP-контракт;
- mapping между ними;
- mapping ошибок;
- mapping progress;
- contract-тесты обоих интерфейсов;
- синхронное версионирование двух моделей.

В результате вместо одного MCP-контракта по всему тракту потребуется сопровождать
REST-контракт, MCP-контракт и правила преобразования между ними.

В данном случае REST-прослойка не снижает нагрузку на сопровождение, а создаёт
дополнительную точку разработки, тестирования, релиза, мониторинга и диагностики.

3. Rate limit

В MCP нет встроенного механизма rate limit. Но это не является недостатком относительно
REST: REST также не определяет rate limit.

Rate limit является функцией HTTP gateway, policy proxy и самого сервиса.

На сервисах Cross-hub, Cross-hub-ext и MCP-DZO ограничения можно устанавливать
отдельно для каждой пары «ДЗО + имя инструмента». Например, для get_weather можно
разрешить 100 запросов в минуту и не более 10 параллельных вызовов, а для create_order
— 10 запросов в минуту и не более 2 параллельных вызовов.

При превышении лимита возвращается HTTP 429 Too Many Requests с указанием времени до
повторной попытки в заголовке Retry-After, например Retry-After: 30.

Сервис MCP-DZO дополнительно ограничивает частоту и количество одновременных вызовов
каждой тулы, чтобы защитить свои ресурсы от перегрузки.

Это одинаково реализуемо и для REST, и для MCP.

4. Валидация запроса и ответа

MCP предусматривает JSON Schema inputSchema для проверки аргументов инструмента. В
версии MCP 2025-11-25 инструмент также может объявить outputSchema для проверки
структурированного результата.

В конфигураторе tool хранятся:

- name;
- description;
- parameters — схема запроса;
- few_shot_examples;
- return_parameters — схема ответа;
- x-type;
- x-version;
- x_payload.

Обработка запроса:

1. Cross-hub передаёт tools/call в ДЗО только в том случае, если toolName разрешён в
   текущей SSD-сессии клиента.
2. Перед передачей запроса в ДЗО Cross-hub дополнительно может валидировать
   params.arguments по схеме parameters, полученной из конфигуратора.
3. После получения ответа Cross-hub дополнительно может валидировать
   result.structuredContent по схеме return_parameters, полученной из конфигуратора.

5. REST до сервиса MCP-DZO с последующим преобразованием в MCP

Если сервис Brain уже является MCP-клиентом, а сервис MCP-DZO является MCP-сервером,
REST-прослойка между ними создаёт два представления одного вызова.

Это приводит к следующим рискам:

- двойное версионирование;
- ошибки преобразования DTO;
- расхождение REST и MCP schemas;
- преобразование моделей ошибок;
- потеря или усложнение progress;
- дополнительная корреляция идентификаторов;
- отдельные тесты mapping;
- дополнительная точка отказа;
- неясное владение контрактом;
- увеличение времени подключения нового tool.

В такой архитектуре REST не добавляет бизнес-функцию. Он только преобразует уже
существующий стандартный MCP-вызов в другой формат и обратно.

Дополнительные преимущества MCP по всему тракту

Снижение стоимости подключения ДЗО. Новое ДЗО реализует стандартный MCP Server и
проходит общие тесты совместимости. Не требуется разрабатывать индивидуальный клиент и
преобразование данных на каждом промежуточном слое.

Отсутствие лишнего преобразования данных. По всему тракту сохраняются:

- JSON-RPC ID;
- tool name;
- arguments;
- progress token;
- result/error;
- schema version.

Это уменьшает количество ошибок преобразования и упрощает диагностику.
